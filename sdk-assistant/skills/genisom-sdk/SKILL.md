# Genisom SDK Development

1. Identify the product and variant from the request or project. For implementation and troubleshooting, also identify the target architecture, SDK release or checkout, and robot system version when compatibility matters. Ask only for missing details that affect the result. A general documentation query only needs the product if the answer depends on it.
2. Use [the SDK document index](references/llms.txt) to select the product and language. If a Markdown export is installed, use its index at `references/markdown/llms.txt` for that snapshot. Read the relevant page, then follow its chapter links as needed. Prefer an explicitly supplied docs checkout or a matching local Markdown export at `references/markdown/<source path>`. Otherwise open the listed official page. If a page is unavailable, ask for the matching SDK headers, examples, or docs checkout. Answer in the user's language. Use the L2 Chinese source for either response language.
3. Use the target SDK's headers and version-matched examples for signatures, headers, libraries, enums, and return values. Use the product documentation for setup, prerequisites, and behavior. For M1, consult its version compatibility page and verify known exceptions against the intended interface. For L1 and L2, verify compatibility from their own release information when available and state what remains unverified. Keep the installed SDK version and the robot system version distinct.
4. Preserve the product's SDK model. L1 uses the Zsibot SDK and its HighLevel interface. Use the L1 reference for UDP, heartbeat, data reporting, and faults. M1 and L2 have product-specific SDKClient references. Verify each method and capability against the target model and release before reusing an example. Distinguish connection or handshake, command acknowledgement, and action or task completion wherever the documentation makes those distinctions.
5. For code requests, reuse the project's build and SDK layout. For a first integration, prefer connecting and reading a documented device or state value before adding motion. Build locally when the matching SDK and toolchain are available. Treat a successful build and a successful hardware run as separate results. Leave execution of robot-connected binaries to the developer unless explicitly authorized for the specific hardware test.
6. Report the intended product and versions, changes or findings, checks performed, and relevant source pages or header paths. Cite only material you read. When using a local draft or export for a detail that may differ from the website, cite the local source and identify the snapshot.
